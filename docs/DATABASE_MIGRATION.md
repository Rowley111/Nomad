# PostgreSQL: схема и перенос данных Nomad Mobile

## Что подготовлено и что ещё не выполнено

Подготовлены отдельный FastAPI API, Alembic-миграция, серверный вход с ролями, хранение общего рабочего пространства и перенос старого JSON через предпросмотр. Действующий React/Vite Static Site сохраняется. Сервер использует тот же JavaScript-модуль проверки и расчётов через Node 22; Docker включает Python и Node.

По снимку настроек владелец добавил `DATABASE_URL`. Сам снимок не подтверждает доступ к PostgreSQL и не показывает, к какому сервису относится переменная. В рабочей среде агента серверный секрет не предоставлен. Подготовка кода не означает, что production-миграция запущена или браузерные данные уже перенесены. Фактические проверки фиксируются в [CHECKS.md](CHECKS.md).

## Где должна находиться переменная

- `DATABASE_URL` — только Environment отдельного **API Web Service**. Переменная в Static Site не создаёт сервер и не переносит данные. Не используйте `VITE_DATABASE_URL` и не вставляйте строку подключения в React, Git, резервный JSON или чат.
- `FRONTEND_ORIGIN` API — точный адрес фронтенда, например `https://nomad-a027.onrender.com`. Несколько разрешённых origin разделяются запятыми; `*` не нужен.
- `VITE_API_URL` Static Site — публичный HTTPS-адрес уже запущенного API, без паролей и без `/api` в конце. Он попадает в bundle по назначению. Пустое значение сохраняет прежний локальный режим.
- `SESSION_HOURS` API — срок серверной сессии, по умолчанию 8 часов. `NODE_BINARY` обычно не требуется: в контейнере доступен `node`.

В Render внутренний PostgreSQL URL предназначен для сервисов того же региона. Для локального ноутбука или внешней облачной среды нужен внешний URL и разрешённое провайдером сетевое подключение. Не отключайте TLS для обхода ошибок. [Документация соединений Render](https://render.com/docs/postgresql-creating-connecting).

## Перед изменением базы

1. На каждом браузере, где есть рабочие записи, откройте прежний сайт → «Настройки» → скачайте полную JSON-копию. Данные localhost, сайта, ноутбука и iPhone могут различаться. Файл содержит коммерческую информацию, храните его вне публичного репозитория.
2. Если PostgreSQL уже содержит данные, сохраните независимый backup средствами провайдера или `pg_dump`. Убедитесь, что выбран правильный сервер/база. Подготовленная миграция добавляет таблицы Nomad, не удаляет старые таблицы; при совпавших именах сначала нужна проверка схемы.
3. Сохраните предыдущий успешный frontend deploy и коммит. Не удаляйте localStorage и прежние JSON-копии после первого успешного импорта.

`pg_dump` должен получать обычный PostgreSQL URI, без SQLAlchemy-суффикса `+psycopg`. Пример при уже безопасно заданной серверной переменной и установленном PostgreSQL client:

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
pg_dump --dbname $env:DATABASE_URL --format custom --file backups/nomad-before-migration.dump
```

Проверьте код завершения и возможность чтения копии через `pg_restore --list`. Файл `*.dump` и каталог `backups/` исключены из Git. Условия серверных резервных копий зависят от плана провайдера; приложение не подменяет их локальным JSON.

## Миграция схемы и первый администратор

Из корня репозитория, на сервере с доступом к нужной базе. `DATABASE_URL` уже должна быть безопасно передана процессу. `.env.example` — образец, Python не загружает его автоматически.

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r server/requirements.txt
.\.venv\Scripts\python.exe -m alembic -c server/alembic.ini upgrade head
.\.venv\Scripts\python.exe -m alembic -c server/alembic.ini current
.\.venv\Scripts\python.exe -m server.cli create-admin
```

CLI запросит имя и пароль скрытым вводом. Публичной регистрации и пароля по умолчанию нет. Для неинтерактивного запуска допускаются временные **серверные** `NOMAD_ADMIN_USERNAME` и `NOMAD_ADMIN_PASSWORD`; после создания удалите их из окружения. В инструкции не храните действующий пароль.

В Linux/контейнере после установки зависимостей:

```sh
python -m alembic -c server/alembic.ini upgrade head
python -m alembic -c server/alembic.ini current
python -m server.cli create-admin
```

Повторный `upgrade head` не создаёт таблицы заново. Создание сотрудника выполняется отдельно: `python -m server.cli create-user --role staff`. Сервер не вызывает `create_all` и не применяет миграции при каждом запуске.

## Отдельный API на Render

1. Используйте существующий подходящий Web Service либо подготовьте отдельный Docker Web Service из того же репозитория, Dockerfile `server/Dockerfile`, Docker context — корень репозитория. Выберите регион существующей PostgreSQL. Пример [render-api.yaml](../render-api.yaml) не применяется автоматически и не меняет Static Site; PostgreSQL в нём не создаётся.
2. Задайте серверные переменные выше. До запуска общей базы выполните миграцию и создание администратора через доступный защищённый shell/задачу либо с компьютера через внешний URL. На Free Web Service нет Shell и one-off jobs: миграцию и создание администратора выполните с компьютера/защищённой облачной среды через внешний URL PostgreSQL. Не помещайте секрет в клиент.
3. Контейнер запускает `uvicorn server.app:app` на `PORT`; путь проверки сервиса `/api/health`. Миграций в Docker build/start command нет. Первый запуск без нужной схемы не считается готовой общей базой.
4. После проверки API без авторизации должен запрещать `/api/workspace`. Войдите администратором и проверьте доступ к пустому workspace.
5. Затем задайте **только** `VITE_API_URL` в действующем Static Site, пересоберите его прежней командой `npm ci && npm run build`, Publish Directory `dist`. Проверьте вход и перенос данных перед работой сотрудников.

Render рекомендует отдельный Web Service для [FastAPI](https://render.com/docs/deploy-fastapi). `preDeployCommand` с миграцией доступен на платных Web Service, Private Service и Worker; на подходящем уже согласованном плане можно настроить `python -m alembic -c server/alembic.ini upgrade head` после backup. Он отсутствует в примере для Free. [Этапы деплоя Render](https://render.com/docs/deploys), [Blueprint reference](https://render.com/docs/blueprint-spec).

Пример явно использует `plan: free`, `autoDeployTrigger: off`; перед ручным применением укажите регион БД. Free имеет ограничения доступности, его нельзя обещать как круглосуточный production. [Ограничения Free](https://render.com/docs/free). Платные ресурсы этой задачей не создаются и не подключаются автоматически.

## Перенос старых данных в общую базу

1. Войдите администратором в облачном режиме. Сотруднику импорт полной базы недоступен.
2. В настройках выберите текущие данные **этого браузера** либо полную JSON-копию другого адреса/устройства.
3. Просмотрите количества добавлений, дубликатов и конфликтов. Перенос объединяет записи: совпадающие ID и ключи прайса не должны бесконтрольно размножаться, отличающиеся существующие записи общей базы сохраняются. Нельзя принять конфликт за удачное обновление — проверьте отчёт.
4. Подтвердите перенос. Сервер повторно проверит текущую ревизию, данные и права. Если другой сотрудник успел сохранить изменения, получите конфликт и заново откройте предпросмотр; чужие изменения не затираются.
5. Проверьте склад, ремонты, убытки и прайс, скачайте полную копию общего workspace. Откройте сайт на втором устройстве под отдельной учётной записью и проверьте общие данные.

Повтор того же файла пропускает уже перенесённые записи. Недостающие исторические суммы/даты не выдумываются: старый статус «Продан» не становится подтверждённой сделкой. Даты бизнес-операций остаются Asia/Almaty. Старые локальные записи после импорта не очищаются.

Обычное серверное сохранение использует ревизию и ID операции. При ошибке сети интерфейс не должен объявлять несохранённые данные успешными или переключаться на скрытый локальный режим. Сессия находится в памяти вкладки; после перезагрузки нужен новый вход. Общая база хранится в PostgreSQL, localStorage остаётся источником миграции/явным локальным режимом.

## Проверки и откат

В дополнение к `npm.cmd test`, `npm.cmd run lint`, `npm.cmd run build` и `npm.cmd run test:ui` после установки серверных зависимостей запустите `.\.venv\Scripts\python.exe -m pytest server/tests` (Linux: `python -m pytest server/tests`). Контракт маршрутов — [server/API.md](../server/API.md), фактические результаты — [CHECKS.md](CHECKS.md). SQLite в тестах не заменяет проверку PostgreSQL. Не называйте production-миграцию выполненной до успешного `upgrade head` на целевой базе.

Для отката приложения верните предыдущий успешный deploy. Аддитивные таблицы лучше оставить до разбора; автоматический `alembic downgrade` может удалить новую историю, поэтому в инструкции он не выполняется. Для возвращения локального frontend уберите `VITE_API_URL` и пересоберите прежний Static Site: общие записи сами в браузер не скопируются, заранее экспортируйте полный JSON из общей базы. Восстановление PostgreSQL из backup — отдельная согласованная операция с проверкой утрачиваемых новых записей.


Проверено по [ограничениям Render Free](https://render.com/docs/free): бесплатная PostgreSQL истекает через 30 дней и не предоставляет встроенные резервные копии. Тариф созданной владельцем базы неизвестен; проверьте срок и независимое резервное копирование до рабочей эксплуатации. Платные ресурсы этой задачей не создавались.
